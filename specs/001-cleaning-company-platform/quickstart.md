# Quickstart: Nuqaa Asir Cleaning Booking & Operations Platform

This guide validates that the feature works end-to-end once implemented. It does not contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for build steps, and `data-model.md` / `contracts/openapi.yaml` for exact schemas.

## Prerequisites

- Node.js 22 LTS, pnpm 9+
- PostgreSQL 16+ running locally (or via Docker)
- `.env` files for `apps/api` and `apps/web` (see Environment Variables below)

## Repository Layout

```text
apps/web        # React + Vite customer portal + admin dashboard
apps/api        # Express + Prisma REST API
packages/shared # Zod schemas, shared TS types, API contract types
```

## Environment Variables

**apps/api/.env**

```text
DATABASE_URL=postgresql://user:pass@localhost:5432/nuqaa_asir
JWT_ACCESS_SECRET=<random>
JWT_REFRESH_SECRET=<random>
JWT_ACCESS_TTL=15m
JWT_REFRESH_TTL=30d
OBJECT_STORAGE_ENDPOINT=<s3-compatible endpoint>
OBJECT_STORAGE_BUCKET=nuqaa-asir-service-images
CORS_ALLOWED_ORIGIN=http://localhost:5173
DEFAULT_LOCALE=ar-SA
DEFAULT_TIMEZONE=Asia/Riyadh
```

**apps/web/.env**

```text
VITE_API_BASE_URL=http://localhost:4000/api/v1
VITE_DEFAULT_LOCALE=ar
```

## Setup

```bash
pnpm install
pnpm --filter apps/api prisma migrate dev
pnpm --filter apps/api prisma db seed
```

**Seed data** (per `data-model.md`) must include: two service areas (Abha, Khamis Mushait), the eight launch service categories from `spec.md` FR-006, one seeded Admin account, a handful of `TimeSlot` rows for the next two weeks, and one non-fiscal `NotificationTemplate` per event in FR-065. Never seed production with a shared/default Admin password.

## Running Locally

```bash
pnpm --filter apps/api dev      # API on :4000
pnpm --filter apps/web dev      # Web on :5173
```

## Validation Scenarios

Each scenario below maps to a User Story in `spec.md` and should be run manually (or via the Playwright E2E suite once implemented) before considering the feature done.

### V1 — Customer registers and submits a booking (User Story 1)

1. Open `http://localhost:5173` in Arabic (default) on a mobile viewport (375×667).
2. Register a new Customer account (`POST /auth/register`).
3. Browse the service catalog, open a service detail page, select property type + size, pick a saved or new address in a served neighborhood, choose an available date/time from `GET /availability`.
4. Submit the booking (`POST /bookings` with an `Idempotency-Key` header). Double-click submit and confirm only one `Booking` row exists (FR-013).
5. Confirm the confirmation screen shows a booking reference and a working WhatsApp click-to-chat link.
6. Switch the UI to English and repeat steps 3–5; confirm layout mirrors correctly and no text overflows on mobile.

**Expected**: `Booking.status = PENDING` (or `DRAFT` if quote still requires manual review), `BookingStatusHistory` has an initial entry, `AuditLog` unaffected (customer actions aren't Admin actions).

### V2 — Admin creates a phone/WhatsApp booking (User Story 2)

1. Log in as Admin.
2. Search for a customer by phone number; if none exists, create one inline (no password set, `status = INVITED`).
3. Complete `POST /bookings/admin` for that customer end-to-end without ever using the customer-facing UI.

**Expected**: Booking appears in the same list/queue as a web-submitted booking, `source = ADMIN_PHONE`.

### V3 — Admin reviews, prices, and confirms (User Story 3)

1. Open a `PENDING` booking flagged `requiresManualReview = true`.
2. Set/override the price with a reason via `POST /bookings/{id}/confirm`.
3. Confirm `Booking.subtotalSnapshot`/`totalSnapshot` are now fixed; change the underlying `Service.basePrice` and re-fetch the booking — snapshot must be unchanged (FR-024).

### V4 — Admin schedules with an internal note and hits capacity (User Story 4)

1. Confirm several bookings into the same `TimeSlot` until `bookedCount = capacity`.
2. Attempt to schedule one more into that slot without `overrideCapacity` — expect `409`.
3. Retry with `overrideCapacity: true` — expect success and a corresponding `AuditLog` entry.
4. Set an `internalHandlingNote` (e.g., "Team A – Hilux 2") and confirm it displays on the day/week calendar view.

### V5 — Admin tracks execution and completes the checklist (User Story 5)

1. On a scheduled booking, call `en-route` → `arrive` → `start` in sequence; confirm each timestamp is set and `status = IN_PROGRESS` only after `start`.
2. Attempt `complete` with required checklist items unanswered — expect `409` listing the outstanding items.
3. Submit all required checklist results, call `checklist/review`, then `complete` — expect `200`, `status = COMPLETED`, and a queued feedback notification log entry.
4. Flag one checklist item as an issue — confirm a `QualityIssue` with `source = CHECKLIST_FAILURE` is created.

### V6 — Customer feedback and rework (User Story 6)

1. As the customer from V1/V5, submit a rating of 2 and a comment.
2. As Admin, confirm the booking's `Review.followUpRequired = true` and a low-rating alert appears in the operations dashboard.
3. File a complaint, categorize it, assign an owner, then create a rework booking via `quality-issues/{id}/rework` — confirm the new booking has `originalBookingId` set and does not require re-entering customer details.
4. Attempt to close the quality issue without `resolution` — expect a validation error; add resolution notes and close successfully.

### V7 — Subscriptions (User Story 7)

1. Create a weekly subscription for a test customer.
2. Trigger the generation job twice in succession (simulating a retry) — confirm exactly the expected number of `Booking` rows exist for the 8-week horizon, no duplicates (unique `(subscriptionId, occurrenceDate)`).
3. Modify a single upcoming occurrence's time; confirm the subscription's own schedule is unaffected.
4. Pause the subscription; confirm no further occurrences generate but existing bookings remain untouched.

### V8 — Reporting (User Story 8)

1. With a known set of seeded bookings/payments, call `/reports/revenue` and `/reports/operations-summary`; manually verify totals against the seed data.
2. Export `/reports/export.csv?report=bookings`; confirm no customer phone/address fields are present unless the report explicitly requires them.

### V9 — Security/Access boundary checks

1. As an unauthenticated client, call any Admin-only endpoint (e.g., `GET /customers`) — expect `401`.
2. As a Customer, call another customer's `GET /bookings/{id}` — expect `403`/`404` (no data leak).
3. Call `GET /bookings/reference/{ref}` without the `token` query param — expect `403`.
4. Grep API logs after running V1–V6 and confirm no full phone number or exact address string appears (FR-078).

### V10 — Arabic/RTL and mobile smoke test

1. Run the full V1 flow at 375px width in Arabic, then again in English, on both the Customer Portal and Admin Dashboard.
2. Confirm no horizontal scroll, all interactive targets ≥44×44px, and calendar/table components in Admin mirror correctly in RTL.

## Running Automated Tests

```bash
pnpm --filter apps/web test        # Vitest + React Testing Library
pnpm --filter apps/api test        # Vitest + Supertest (requires test DB)
pnpm e2e                           # Playwright, runs V1–V9 above
```

## Build & Deploy Smoke Check

```bash
pnpm --filter apps/api build && pnpm --filter apps/api start
pnpm --filter apps/web build       # verify public routes (home, catalog, service detail) are pre-rendered per research.md R9
```

Confirm the built `apps/web/dist` contains static HTML for `/`, `/services`, and `/services/{slug}` (not just an empty `<div id="root">`), validating the SEO/CWV mitigation from `research.md` R9.
